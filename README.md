# README — the bamr87 context engine

> Context engine for the bamr87 fleet: crawlers and distillers that build queryable docs for every project, incl. MCP.

[![CI](https://github.com/bamr87/README/actions/workflows/ci.yml/badge.svg)](https://github.com/bamr87/README/actions/workflows/ci.yml) [![License](https://img.shields.io/github/license/bamr87/README)](LICENSE) [![Live site](https://img.shields.io/badge/live-bamr87.github.io%2FREADME-2ea44f)](https://bamr87.github.io/README/)

## Overview

The consolidated README of the [bamr87/bamr87](https://github.com/bamr87/bamr87) monorepo: a set of crawlers, distillers, and gates — with AI orchestration hooks and an MCP query surface — that continuously build and maintain the context describing every submodule in the fleet.

Instead of hand-writing documentation *about* the fleet, this repo **grows it**: crawlers aggregate each project's markdown, the engine distills the corpus upward into a pyramid of context, and an MCP server makes the whole thing queryable by AI clients. The pyramid is regenerated on a schedule, so the context evolves as the fleet does.

## Features

- One `collect` stage that gathers each repository's official documentation into `docs/`, an Obsidian vault
- A second brain in `docs/brain/`: generated concept and project notes, a hot cache, a change log and vault health
- Obsidian's views on the published site: graph, local graph, backlinks, hover previews, quick switcher, canvas
- A distiller that builds a context pyramid: a fleet README, one card per project and structured facts
- A queryable index with a CLI and an MCP server (`mcp/server.py`) for AI clients
- Scheduled regeneration so the context evolves with the fleet
- Every governed directory carries a `SCHEMA.md` structure contract

## The pyramid

```
        ▲  L0  context/README.md   the consolidated fleet README (apex)
       ▲▲  L1  context/cards/      one distilled card per project
      ▲▲▲  L2  context/facts/      structured facts (machine layer)
     ▲▲▲▲  L3  docs/               aggregated markdown corpus (base)
    ─────  query: context/index/ · CLI · MCP server (mcp/server.py)
```

Every governed directory carries a `SCHEMA.md` (structure table + rules), mirroring the parent monorepo's pyramid protocol; `scripts/schema_lint.py check .` is the drift gate. Structural facts live in the registry (`_data/projects.yml`) — generated surfaces (`context/`, `docs/`, `repos.txt`, the span below) are regenerated, never hand-edited.

## Quick start

```bash
pip install -r requirements.txt        # pyyaml, requests, nltk, pytest
pip install -r requirements-docs.txt   # optional: MkDocs site build

# 1. Collect the corpus (clones every repo in the registry)
python3 -m scripts.context_engine collect

# 2. Build the context pyramid (offline; AI enrichment auto-enables on keys)
python3 -m scripts.context_engine build

# 3. Query it
python3 -m scripts.context_engine query jekyll theme
python3 -m scripts.context_engine card bashcrawl
python3 -m scripts.context_engine nav bashcrawl --depth 2
python3 -m scripts.context_engine status
```

AI clients query the same pyramid through MCP — the server is registered in [`.mcp.json`](.mcp.json), so Claude Code picks it up automatically in this repo. Tools: `list_projects`, `get_project`, `search_context`, `get_readme`, `get_nav`, `get_schema`, `context_status`. See [mcp/README.md](mcp/README.md).

## How it works

| Stage | Input | Output | Entry point |
|---|---|---|---|
| 1. Collect | `_data/projects.yml` | `docs/{project}/` corpus (L3), links woven | `python3 -m scripts.context_engine collect` |
| 2. Validate | `docs/` | reports + in-place fixes | `scripts/run_doc_checks.sh` |
| 3. Index | `docs/` | `docs/docs_index.json` | `scripts/generate_docs_index.py` |
| 4. Brain | `docs/` + registry `brain:` + `notes/` | `docs/brain/`, `docs/.obsidian/` | `scripts/context_engine/brain.py` |
| 5. Navigate | `docs/` + registry `navigation:` | `nav.yml`, `context/nav/`, `docs/browse/` | `scripts/context_engine/navigator.py` |
| 6. Distill | corpus + registry + nav | `context/` pyramid (L2→L0) | `python3 -m scripts.context_engine build` |
| 7. Serve | `context/` | CLI + MCP answers | `mcp/server.py` |
| 8. Publish | `docs/` + `context/vault/graph.json` | the site, with Obsidian's views | `brain_site/hook.py` |

Ingest normalizes as it writes: upstream `icon:` frontmatter is mapped onto bundled Material icons (`scripts/fix_frontmatter_icons.py`) and soft-wrapped prose is unwrapped (`tools/unwrap-prose.py`), so each crawled page lands in a state the navigation and the `markdown-oneline` gate already accept.

The engine (`scripts/context_engine/`) runs **extract → brain → navigate → synthesize → assemble → index → graph**, firing hooks from [`hooks.d/`](hooks.d/README.md) at each stage. Enrichment is provider-agnostic: with an Anthropic credential (`ANTHROPIC_API_KEY`, or Claude Code OAuth via `CLAUDE_CODE_OAUTH_TOKEN` / `ANTHROPIC_AUTH_TOKEN`) or an xAI one (`XAI_API_KEY` / `GROK_API_KEY`) set, cards and the apex get AI-distilled prose; with no key the build is fully heuristic and deterministic. Rebuilds are diff-stable — outputs carry corpus fingerprints, not timestamps.

## The second brain

`docs/` is an Obsidian vault: open that folder in Obsidian and the graph, backlinks, canvas and Bases work straight away, with one colour per repository. The published site shows the same vault with the same links, because the crawl, the site and MCP all resolve links through `scripts/context_engine/vault.py`.

The pattern follows [claude-obsidian](https://github.com/AgriciDaniel/claude-obsidian) and Karpathy's LLM wiki. Sources stay as their repositories wrote them, and generated notes compound on top:

- **Concepts** (`docs/brain/concepts/`): a tag becomes a note once enough pages share it, and a `[[link]]` nothing answers becomes a stub once enough pages ask for it. These connect repositories that never link to each other.
- **Projects** (`docs/brain/projects/`): one note per repository, with its most connected pages and shared concepts.
- **Hot cache, log and health** (`hot.md`, `log.md`, `health.md`): what changed, what connects, and what is broken.
- **Notes** (`notes/`): the only hand-written part, for knowledge that spans repositories.

```bash
python3 -m scripts.context_engine hot
python3 -m scripts.context_engine note "Docker"
python3 -m scripts.context_engine lint
```

Agents get the same reads over MCP (`get_hot`, `get_note`, `get_neighbours`, `vault_lint`), and `.claude/skills/second-brain/` tells Claude Code how to query, save, ingest and lint.

## Continuous evolution

- **`aggregate-docs.yaml`** (cron + manual) re-crawls the fleet, rebuilds the pyramid, and commits the result — the context grows without anyone editing it.
- **`docs-quality-check.yaml`** runs on every PR: the SCHEMA drift gate, the navigation drift gate (`context_engine navcheck`), and the tracked-surfaces integrity gate (`scripts/check_tracked_surfaces.py`), then lints the corpus and posts a report. The cron runs the same three gates before it commits.
- **`deploy-pages.yaml`** publishes `docs/` (whose home page is the generated fleet overview) to [bamr87.github.io/README](https://bamr87.github.io/README/).
- **Hooks** (`hooks.d/<stage>/`) let agents and automation extend every build — the freshness report (`post_index`) and the schema gate (`post_build`) ship as examples.

## The fleet documentation review

The survey also consolidates the fleet's documentation for review. `python3 -m scripts.context_engine survey --workspace <dir>` reads every checkout under `<dir>` — each on whatever branch it is on, so a set of open documentation PRs can be reviewed together; a symlink to a folder inside another checkout (a monorepo package such as zer0-CMS's `packages/zer0-mistakes/`) is reviewed in place on that checkout's branch — and writes [`context/reports/docs_review.md`](context/reports/docs_review.md): every repository's documents with their one-line summaries and sizes, the words in the files every agent session loads, and each repository's standing against the hub's [documentation framework](https://github.com/bamr87/bamr87/blob/main/specs/DOCS.md) (UPS-DOC). The weekly `survey` writes the same review from the default branches beside `fleet_health`. The checks reuse the hub's generator, vendored here as `tools/docs_index.py`, so the review and each repository's own `--check` agree.

## Growing the fleet

1. Add the project to [`_data/projects.yml`](_data/projects.yml) (name, repo, url, seed description, topics; optionally `nav:` for sidebar grouping and `collect:` for what counts as official documentation).
2. `python3 -m scripts.context_engine collect <name> && python3 -m scripts.context_engine build` — or just wait for the scheduled workflow.

## Development

```bash
python tests/test_runner.py --type quick     # unit suite
python3 scripts/schema_lint.py check .       # structure drift gate
python3 -m scripts.context_engine navcheck   # nav.yml / context/nav / docs/browse match the corpus
python3 scripts/check_tracked_surfaces.py    # every surface names only git-tracked files
bash scripts/run_doc_checks.sh               # corpus quality checks
python3 tools/unwrap-prose.py --check --exclude '(^|/)SCHEMA\.md$' --exclude '(^|/)CHANGELOG\.md$' --exclude '^docs/'   # one paragraph per line (markdown-oneline.yml scope)
```

If `navcheck` fails, run `python3 -m scripts.context_engine build` and commit the regenerated surfaces. Don't edit them by hand.
